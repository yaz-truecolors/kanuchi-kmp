# 要求から main 反映までの開発フロー（AIDD）設計書

利用者が入力した1つの要求を、エージェントが要件定義から main への反映まで進めるための運用の設計です。
このフローを実行するスキル群（「11. スキルの構成」）を作る前の設計として、運用のルールと判断の基準をここに決めます。

- 状態: 設計確定（スキルは未作成）。設計の途中で決めた事項は「13. 決定事項」にまとめる。
- 既存の PR 手順（`AGENTS.md`「Pull Request 作成手順」）・レビュー手順（skill `pr-review`）を土台にし、それと違う点は
  「12. 既存の規約・設定の変更」で規約側を直す。

## 1. 方針

| 方針 | 内容 |
|---|---|
| 人は意図と設計を判断し、エージェントは実装を担う | 人の確認は「要件の確定」「外部設計と単位分割の確認」「main への反映の承認」の3回に絞る。それ以外はエージェントが自律的に進める |
| 検証を実装から独立させる | 受け入れ条件を要件定義の段階でテストできる形で書き、テストを実装より先に作る。レビューは実装の文脈を持たないサブエージェントが行う |
| 合否は機械で判定できる条件にする | 各段階の完了条件（ゲート）は、CI の結果・レビューの指摘の重大度・テストの結果など、エージェントが自分で判定できるものにする |
| 状態は会話ではなくファイルと PR に持たせる | コンテキストの圧縮やセッションのまたぎがあっても、`PLAN.md` と PR を読めば再開できるようにする |
| ループには必ず上限を付ける | レビューの往復・戻りの回数に上限を設け、超えたら止めて人に知らせる |
| 要件の変更は必ず人に返す | `REQUIREMENTS.md` を書き換える必要が出たら、作業を止めて判断を仰ぐ |

## 2. 用語

| 用語 | 意味 |
|---|---|
| 要求 | 利用者が入力する「やりたいこと」。1つの要求に1つの要求 ID・親ブランチ・親 PR が対応する |
| 要件定義 | 要求を、受け入れ条件・スコープ・対象外を持つ確定した仕様にする段階。成果物は `REQUIREMENTS.md` |
| 外部設計 | 利用者から見える振る舞い（画面・操作・データ・権限）の設計。アプリ全体の外部設計書への加筆・新規追加として書く |
| 単位 | 外部設計を、独立して検証・マージできる大きさに分けたもの。1単位＝1つの単位 PR |
| 親ブランチ / 親 PR | 要求ごとのブランチと、それを main に向けた PR。要件定義・外部設計の差分を持ち、各単位がマージされていく |
| 単位 PR | 単位ごとのブランチを親ブランチに向けた PR。詳細設計・テスト・実装を持つ |
| ゲート | 次の段階に進むための完了条件 |

## 3. 全体の流れ

```
[P1 要件定義] ── 人と対話 ──▶ G1: 人が要件を確定
      │
[P2 外部設計・単位分割] ──▶ 親ブランチ・親 PR（Draft）を作成 ──▶ G2: 人が設計と分割を確認
      │
[P3 単位ループ]  単位 1 → 単位 2 → … （PLAN.md の順）
      │   U1 詳細設計 → U2 テスト作成 → U3 実装 → U4 単位 PR → U5 レビューと修正のループ
      │   → U6 親へマージ → U7 結合テスト（親ブランチ）→ 次の単位
      │
[P4 取りまとめ] ──▶ 全体の結合テスト・承認依頼の資料 ──▶ G3: 人が承認し main へマージ
```

戻りの規則は「8. 戻りと中断」、状態の持ち方は「9. 状態管理と再開」。

## 4. 成果物と置き場所

| 成果物 | 置き場所 | 作る段階 | 役割 |
|---|---|---|---|
| 要件定義 | `docs/requests/<要求ID>/REQUIREMENTS.md` | P1 | その要求の受け入れ条件・スコープ・対象外。自律作業の範囲を決める「契約」 |
| 計画 | `docs/requests/<要求ID>/PLAN.md` | P2 | 単位の一覧・依存関係・状態・PR 番号・レビュー回数。再開の起点 |
| 決定記録 | `docs/requests/<要求ID>/DECISIONS.md` | P2〜P4 | 設計・実装の段階に戻ったときの理由と内容、採用しなかったレビュー指摘のうち設計に関わるもの |
| 外部設計 | `docs/design/<機能>.md`（画面・機能ごとに1ファイル。例: `docs/design/daily-input.md`） | P2（P3 で修正することがある） | 現在の仕様の正本。要求ごとの差分は、既存のファイルへの加筆か新しいファイルとして入る |
| 詳細設計 | 単位 PR の本文（「詳細設計」の節）＋テスト＋コード | U1 | 単位の中だけで閉じる設計。独立したファイルにはしない（ファイルの増えすぎを防ぐ） |
| テスト | 各モジュールのテスト・`supabase/tests/database/` | U2 | 受け入れ条件と詳細設計から作る |

要求 ID は `YYYYMMDD-<短い英語の名前>`（例: `20261105-monthly-export`）とする。日付は要件定義を始めた日。

`docs/requirements.md` は背景・目的・方針（why）を記録する場所とし、現在の仕様の記述（「6. DBスキーマ」「9. 日次入力・集計の仕様」等）は
`docs/design/` へ移す（「12. 既存の規約・設定の変更」）。

## 5. 各段階の定義

### P1 要件定義（人と対話）

- **入力**: 利用者の要求、`docs/requirements.md`、アプリ全体の外部設計書、関連するコード
- **作業**: 要求の意図・利用者・使う場面を質問で確かめ、`REQUIREMENTS.md` を書いて見せ、合意するまで直す
- **`REQUIREMENTS.md` の構成**:
  - 背景・目的
  - スコープ（やること）と対象外（やらないこと）
  - 受け入れ条件（テストできる形。例: 「〈前提〉のとき、〈操作〉すると、〈結果〉になる」）。ID（`AC-01` 等）を振る
  - 権限（誰が参照・変更できるか）、データ（新しく持つ情報・既存の情報への影響）
  - 既存の機能への影響、未決のまま進めてよい事項（設計の段階でエージェントが決めてよいこと）
- **G1（人）**: 利用者が「確定」と明示する。確定前に親ブランチ・親 PR は作らない

### P2 外部設計・単位分割

- **作業**:
  1. 外部設計書に、要求の差分（加筆または新規の節）を書く。受け入れ条件 ID との対応を付ける
  2. 単位に分け、`PLAN.md` を作る（分割の基準は下）
  3. 親ブランチ `req/<要求ID>` を main から作り、`REQUIREMENTS.md`・`PLAN.md`・外部設計の差分をコミットして、
     main に向けた親 PR を Draft で作る
- **単位の分割の基準**:
  - 縦に切る: 1つの単位が DB → data → domain → ViewModel → 画面を必要な分だけ通して持ち、単位をマージした時点で
    親ブランチが壊れていない（`verify` が通る）状態にする。層ごと（「DB だけ」「画面だけ」）には切らない
  - 大きさの目安: 差分 400 行程度まで（テストを含む）。超える見込みならさらに分ける
  - 順番: 依存関係で決める。各単位に、担当する受け入れ条件 ID を割り当て、すべての受け入れ条件がどれかの単位に割り当たっていること
- **G2（人）**: 外部設計の差分と `PLAN.md` を利用者に見せ、確認を得る（ここが一番安く直せる時点のため）。
  指摘があれば P2 を直して再確認する。要件に関わる指摘なら P1 に戻る

### P3 単位ループ（単位ごとに繰り返す）

各単位は、実装の文脈を持ち越さないよう新しいコンテキスト（サブエージェントまたは新しいセッション）で実行する。
入力は `REQUIREMENTS.md`・外部設計書・`PLAN.md` の該当単位・親ブランチの最新の状態。

| 手順 | 作業 | 完了条件 |
|---|---|---|
| U1 詳細設計 | 単位ブランチ `unit/<要求ID>/<連番>-<名前>` を親ブランチから作る。変更する層・クラス・テーブル・関数と、エラー時の振る舞いを決める | 詳細設計を単位 PR の本文に書ける状態 |
| U2 テスト作成 | 受け入れ条件と詳細設計からテストを先に書く（domain・data・ViewModel・DB テストのうち該当するもの）。UI の見た目・操作は自動テストの対象外（`copilot-construction.md`「4. テスト・検証」） | 新しいテストが、実装が無いために失敗することを確認した |
| U3 実装 | テストが通るように実装する | `./gradlew verify` と、`supabase/` を変えた場合は `./supabase/tests/run.sh` がローカルで成功 |
| U4 単位 PR | 親ブランチに向けて Draft で作る。本文に詳細設計・担当する受け入れ条件 ID・確認方法を書く | CI（`build-lint-test`・`db-test`）が成功（「6. ブランチと PR」の CI の変更が前提） |
| U5 レビューと修正 | skill `pr-review` でレビューし、指摘に対応する（「7. レビューの終了条件」） | 終了条件を満たす |
| U6 親へマージ | 単位 PR を親ブランチへマージする（エージェントが行ってよい） | マージ後に `PLAN.md` の状態を「完了」にしてコミット |
| U7 結合テスト | 親ブランチで `verify`・DB テストを実行する。画面の確認（`local-ui-check`）は P4 でまとめて行う | すべて成功。失敗したら原因の単位に戻る（「8. 戻りと中断」） |

単位は `PLAN.md` の順に1つずつ進める（並行して進めない）。

### P4 取りまとめと承認

- **作業**:
  1. 親ブランチを main に追従させ（「6. ブランチと PR」）、親ブランチ全体で `verify`・DB テストを実行し、skill `local-ui-check` で
     すべての受け入れ条件のシナリオを画面で確認する。問題が見つかったら、受け入れ条件 ID から担当の単位を `PLAN.md` で特定し、その単位に戻る
  2. 親 PR を skill `pr-review` でレビューする（単位をまたぐ問題を見るため。終了条件は U5 と同じ）
  3. 承認依頼の資料を親 PR の本文に書く:
     - 受け入れ条件 → 単位 PR → テスト・確認結果の対応表
     - 画面の変更のスクリーンショット（`local-ui-check`）
     - 各単位のレビューの結果（指摘の件数と、採用しなかった指摘とその理由）
     - `DECISIONS.md` の要約（途中で戻った箇所）
  4. 親 PR の Draft を解除し、利用者に承認を依頼する
- **G3（人）**: 利用者が親 PR を確認し、main へマージする（main へのマージは人が行う。`AGENTS.md`「4.」）

## 6. ブランチと PR

| 項目 | 決め事 |
|---|---|
| 親ブランチ | `req/<要求ID>`。main から作る |
| 単位ブランチ | `unit/<要求ID>/<連番2桁>-<名前>`。親ブランチから作る（前の単位がマージされた後の親ブランチから作る）。`req/<要求ID>/...` にしないこと（Git は `req/<要求ID>` というブランチがあると、その下に `req/<要求ID>/...` を作れない） |
| 単位 PR | 親ブランチ向け・Draft。エージェントがマージしてよい |
| 単位 → 親のマージ方式 | squash（1単位＝親ブランチの1コミットにして、親 PR の履歴を読める形にする） |
| 親 → main のマージ方式 | merge commit（main に単位ごとのコミットを残し、どの単位で何が入ったかを main の履歴でたどれるようにする） |
| main への追従 | 単位を親にマージするたびに、main の新しいコミットを親ブランチへマージする（rebase は単位 PR の基点を壊すため使わない） |
| CI | `ci.yml` の起動条件に親ブランチを加え、単位 PR でも `build-lint-test`・`db-test` が動くようにする（現状は main 向けの PR だけ。「12.」） |
| マイグレーション | 単位ごとに新しいマイグレーションファイルを追加する。親ブランチで先にマージされた単位のマイグレーションは「適用済み」として扱い、変更しない（`supabase.instructions.md`「マイグレーション運用」と同じ考え方） |

## 7. レビューの終了条件

レビューは skill `pr-review` で行う。このスキルは会話履歴を持たないサブエージェントで動くため、実装した側の文脈に引っ張られない。
レビューには差分・`REQUIREMENTS.md`・外部設計書・単位 PR の本文（詳細設計）だけを渡し、「なぜそう実装したか」は渡さない。

**終了条件（すべて満たしたら単位を完了にする）**:

1. 🔴 必須の指摘が 0 件（未対応のものが無い）
2. 🟡 推奨・❓ 質問の指摘が、すべて「採用（修正コミットあり）」か「採用しない（理由を返信）」で決着している
3. ⚪ 軽微の指摘は終了をさまたげない（対応するかはエージェントが判断し、スレッドには必ず返信する）
4. 最後のレビューの後に入れた修正が軽微の範囲だけで、CI が成功している。軽微を超える修正を入れたら、もう一度レビューする

**上限**: レビューの往復は1単位につき 3 回まで。3 回目のレビューでも 🔴 が残る場合は、その単位を止めて `PLAN.md` に「要確認」と書き、利用者に知らせる。
同じ指摘（同じ箇所・同じ内容）が2回続いた場合も、修正の方針が合っていないとみなして止める。

件数（例: 「指摘が3件未満」）では判定しない。同じ差分でもレビューのたびに件数がぶれ、PR の大きさによっても意味が変わるため。

## 8. 戻りと中断

不都合が見つかったときは、そのレベルに応じて戻る。要件レベルだけは自律的に解消せず、作業を止める。

| レベル | 判定の基準 | 対応 |
|---|---|---|
| 要件 | `REQUIREMENTS.md` の受け入れ条件・スコープ・対象外・権限・データのどれかを変える必要がある。または、受け入れ条件どうしが矛盾する・受け入れ条件を満たす実装ができない | **作業を止める**。何が問題か・選択肢・それぞれの影響を利用者に示して判断を仰ぐ。決まったら `REQUIREMENTS.md` を直し、P2 からやり直す範囲を `PLAN.md` に書く |
| 外部設計 | 利用者から見える振る舞いを変えるが、受け入れ条件の範囲に収まる | 外部設計書を直す（親ブランチへの直接のコミット、または単位 PR に含める）。影響する単位を `PLAN.md` で「やり直し」にする。`DECISIONS.md` に記録 |
| 詳細設計・実装 | 単位の中で閉じる | 単位の中で U1〜U3 に戻る。単位 PR の本文の詳細設計を直す |

判定に迷う場合は、上のレベルとして扱う（要件か外部設計か迷ったら要件として止める）。

## 9. 状態管理と再開

`PLAN.md` を状態の正本とし、状態が変わるたびに親ブランチ（単位の作業中は単位ブランチ）へコミットする。

```markdown
# <要求ID> 計画

- 親 PR: #<番号>
- 状態: P3 単位ループ（単位 2 / 4）

| 連番 | 単位 | 受け入れ条件 | 依存 | 状態 | 単位 PR | レビュー回数 |
|---|---|---|---|---|---|---|
| 01 | 案件の一覧に検索を追加 | AC-01, AC-02 | - | 完了 | #61 | 2 |
| 02 | 検索条件の保存 | AC-03 | 01 | レビュー中 | #62 | 1 |
| 03 | ... | AC-04 | 02 | 未着手 | - | - |
```

- 状態: 未着手 / 詳細設計中 / 実装中 / レビュー中 / 完了 / やり直し / 要確認
- 再開するときは、`PLAN.md` と各 PR（未解決のスレッド・CI）を読んで、次にやることを決める（会話の記憶に頼らない）。

## 10. 停止条件と上限

| 条件 | 対応 |
|---|---|
| 要件レベルの不都合（「8.」） | 止めて利用者に判断を仰ぐ |
| 1単位のレビューが 3 回を超える、同じ指摘が2回続く（「7.」） | その単位を「要確認」にして止める |
| 同じ単位の「やり直し」が 2 回を超える | 分割か設計が合っていないとみなし、P2 の見直しを利用者に相談する |
| CI・`verify` が環境の問題（JDK・Docker・Chrome が無い等）で動かない | 止めて利用者に知らせる（検証できないまま進めない） |
| main への追従でコンフリクトし、他の PR の意図が分からない | 止めて利用者に知らせる |

## 11. スキルの構成

1つの大きなスキルにせず、段階ごとに分ける。全体を進める役は `PLAN.md` を見て、次に呼ぶスキルを決めるだけにする。

| スキル | 担当 | 実行のしかた |
|---|---|---|
| `req-define` | P1 要件定義（利用者との対話）と G1 | 呼び出したセッションで対話する |
| `req-plan` | P2 外部設計・単位分割・親 PR の作成と G2 | 呼び出したセッションで行い、G2 で利用者に確認する |
| `req-unit` | P3 の1単位（U1〜U7） | 単位ごとに新しいコンテキストで実行する。レビューは `pr-review` を呼ぶ |
| `req-finish` | P4 取りまとめと承認依頼 | 親 PR の資料を作り、利用者に承認を依頼する |
| `req-run`（全体を進める役） | `PLAN.md` を読み、次の段階のスキルを呼ぶ。ゲートと停止条件を判定する | 再開のときもこれを呼ぶ |

## 12. 既存の規約・設定の変更

このフローを導入するときに、あわせて直す必要があるもの。

| 対象 | 変更 | 理由 |
|---|---|---|
| `.github/workflows/ci.yml` | `pull_request` の `branches` に親ブランチ（`req/**`）を加える | 単位 PR で CI が動かないため。必須チェックのジョブ名は変えない（`ci.instructions.md`） |
| `AGENTS.md`「4.」 | 「エージェントはマージしない」に、「このフローの単位 PR を親ブランチへマージする場合を除く」を加える | 単位 PR をエージェントがマージするため |
| `AGENTS.md`「1.」〜「3.」 | 単位 PR も同じ手順（Draft・CI・レビュー対応）に従うことと、ベースが親ブランチになることを書く | 手順の正本をそろえる |
| `.claude/skills/pr-review/SKILL.md` | PR が無いときの差分を `main...HEAD` ではなく PR のベース（親ブランチ）との差分にする。レビューの入力に `REQUIREMENTS.md`・外部設計書を加える | 単位 PR のベースが main ではないため。仕様との照合のため |
| `docs/requirements.md`・`docs/design/` | 現在の仕様の記述（「6. DBスキーマ」「9. 日次入力・集計の仕様」等）を `docs/design/` の機能ごとのファイルへ移し、`docs/requirements.md` には背景・目的・方針と `docs/design/` への案内を残す | 同じ内容が複数の場所に書かれるのを防ぐ。このフローの P2 が `docs/design/` を前提にするため、最初の要求より前に行う |
| `copilot-construction.md`・`.github/instructions/` | 索引に `docs/requests/`・`docs/design/` の位置付けを加え、`docs/requirements.md` の節を参照している箇所を移した先に直す | エージェントが参照先を迷わないため |

## 13. 決定事項

設計の途中で選択肢から決めた事項と、その理由。運用してみて合わなければ見直す（「14.」の5）。

| 事項 | 決定 | 選ばなかった選択肢 | 理由 |
|---|---|---|---|
| 外部設計書の置き場所と構成 | `docs/design/` に画面・機能ごとのファイル。`docs/requirements.md` の仕様の節を移す | 1ファイル（`docs/design.md`）、`docs/requirements.md` の拡張 | 要求ごとの差分が機能ごとのファイルに分かれ、PR で読みやすい。背景（why）と仕様を分けられる |
| G2（外部設計・単位分割の確認） | 入れる | 入れない | 実装の前の、一番安く直せる時点で設計のずれを直すため |
| 要求 ID の採番 | 日付＋名前（`YYYYMMDD-<名前>`） | 連番、GitHub Issue 番号 | ID を見て中身が分かり、他の仕組みに依存しない |
| 単位の大きさの目安 | 差分 400 行程度（テストを含む） | 200 行、800 行 | レビューが一度に見通せ、縦に切っても小さな機能なら収まる |
| レビューの往復の上限 | 1単位につき 3 回 | 2 回、5 回 | 3 回で 🔴 が残るなら、設計か修正の方針が合っていない可能性が高い |
| 親 → main のマージ方式 | merge commit | squash | 単位ごとの区切りを main の履歴に残すため |
| 画面の確認（`local-ui-check`）の時期 | P4 でまとめて行う | 画面のある単位ごと | 単位ごとの確認にかかる時間を省く。代わりに、問題が見つかったときは受け入れ条件 ID から戻る単位を特定する（P4 の1） |
| 単位の並行実行 | 直列（1単位ずつ） | 最初から並行 | マージの順番・コンフリクト・マイグレーションの並び順の管理を避ける。運用に慣れてから並行化を検討する |

## 14. 導入の進め方

1. `docs/requirements.md` の仕様の節を `docs/design/` へ移す（「12.」の `docs/requirements.md`・`docs/design/` と `copilot-construction.md` の行）
2. 「12.」の残りの規約・設定の変更（特に `ci.yml` と `AGENTS.md`）を1つの PR で入れる
3. `req-define` と `req-plan` を作り、小さな要求1件で P1〜P2 だけを試す
4. `req-unit` を作り、同じ要求の単位を1つだけ通して試す。レビューの終了条件・上限が妥当かを見直す
5. `req-finish` と `req-run` を作り、要求1件を最後まで通す。途中で人が介入した箇所を記録し、この設計書に反映する
