# PR レビュー（指摘を PR 上に記録する）

本リポジトリの PR をレビューし、指摘を GitHub の PR 上に残すための手順です。

レビュー対象の指定（引数）: `$ARGUMENTS`（空なら下の「0. 対象とモードを決める」に従う）

## 実行のされ方

- このスキルは、呼び出したセッションの会話履歴を持たないサブエージェント（`context: fork`）で実行される。
  呼び出し元で「なぜその変更をしたか」は分からない前提で、PR 本文・コミット・コード・規約ファイルだけを根拠に、初めて見るつもりでレビューする。
- 途中でユーザーに確認せず、レビューから投稿（再レビューではスレッドへの返信・Resolve を含む）までをこのサブエージェントで行う。
  呼び出し元は終わるまで待つ（`background: false`）。裏で動かすと、呼び出し元がレビューの投稿前に CI の成功だけを見て
  Draft を解除するなど、先へ進んでしまうため。
- 確認なしで使えるコマンドは frontmatter の `allowed-tools` に限っている。GitHub の GraphQL は `gh api graphql` を直接使わず、
  操作を一覧・返信・Resolve に固定した `scripts/threads.py` 経由で使う（`gh api graphql` を許可すると、Ready 化・マージ等の
  mutation まで確認なしで実行できてしまうため）。ファイルも書かない（投稿内容は標準入力で渡す）。
- 行うのはレビューと PR への記録だけ。コードの修正・コミット・push、作業ツリーのブランチの切り替え、Draft の解除、
  レビュアーの指定・レビュー依頼、マージは行わない。
- 終わったら、呼び出し元へ次の内容を返す（呼び出し元はこれをユーザーに伝える）。
  - 投稿したレビューの URL（セルフレビューのモードでは無し）
  - 指摘の一覧（ID・種別・場所・1行の要約）。再レビューでは、前回までの指摘の状態も
  - 確認していないこと、途中で失敗した手順があればその内容

- **観点の正本**: 本アプリ固有の「指摘しない事項」「重点的に確認すべき事項」は
  [.github/skills/code-review/SKILL.md](../../../.github/skills/code-review/SKILL.md)（Copilot・人間のレビューと共通）を正とし、
  ここには重複して書かない。このファイルには、標準的な観点と、レビューの進め方・PR への記録の仕方だけを書く。
- **記録の形**: 指摘は1件ずつ行コメント（レビュースレッド）にし、PR 作成者が各スレッドで「採用（修正コミット）／採用しない（理由）」を
  返信して Resolve する（`AGENTS.md`「3. レビューフィードバックに対応する」）。レビューの全体像は概要コメントに表で残す。
  後から PR を見た人が「何を指摘され、どう対応したか」をスレッドと概要コメントだけで追えるようにする。

## 0. 対象とモードを決める

| 指定 | 対象 | モード |
|---|---|---|
| PR 番号（例: `/pr-review 53`） | その PR | PR に過去のこのスキルのレビュー（概要コメントに `<!-- pr-review:` を含む）が無ければ**初回**、あれば**再レビュー** |
| 指定なし | 今のブランチの PR（`gh pr view --json number`） | 同上 |
| 指定なしで PR が無い | `git diff main...HEAD` と未コミットの変更（`git status --short` で未追跡のファイルも確認する） | **セルフレビュー**（PR が無いので投稿せず、結果を呼び出し元に返すだけ） |

情報を集める（PR の場合）。

```sh
gh pr view <N> --json number,title,body,url,author,isDraft,baseRefName,headRefName,headRefOid,files,reviews
gh pr diff <N>
gh pr checks <N>
```

- 未解決・解決済みのレビュースレッドを取得する（既存の指摘との重複を避けるため、初回でも取得する）。

  ```sh
  python3 -I .claude/skills/pr-review/scripts/threads.py list <N>
  ```
- 変更後のファイル全体を読む（差分だけで判断しない）。今のブランチが PR の head と同じなら作業ツリーを読み、違う場合は
  `git fetch origin pull/<N>/head` してから `git show <headRefOid>:<path>` で読む。作業ツリーのブランチは切り替えない。
- レビューの基準にした `headRefOid` を控えておく（投稿時に、レビュー中に push されていないかの確認に使う）。

## 1. 規約を読む

1. `copilot-construction.md`（全領域共通）と `.github/skills/code-review/SKILL.md`（観点の正本）を読む。
2. 変更ファイルのパスに対応する領域別ファイル（`.github/instructions/<領域>.instructions.md`。索引は `copilot-construction.md`
   「領域別の規約ファイル（索引）」）を、**該当するものはすべて**読む。
3. 仕様に関わる変更（画面の振る舞い・計算・権限）は `docs/requirements.md` の該当節も読み、PR 本文の「背景」と照らし合わせる。

## 2. レビューする

PR 本文（概要・変更内容・確認方法・チェックリスト）と差分を照合したうえで、次の2種類の観点で確認する。
変更が大きい（目安: 変更ファイル 20 以上）場合は、領域（`supabase/`・`data/`・`domain/`・`presentation/` 等）ごとに区切り、
領域ごとにその領域別ファイルを読み直してから順にレビューする。

### 標準的な観点

| 観点 | 確認すること |
|---|---|
| 正しさ | 仕様（PR 本文・`docs/requirements.md`）どおりか。境界値（0・空・月末・年またぎ・上限）、null、状態の組み合わせ、失敗時の状態の戻し方 |
| エラー処理 | 失敗が握りつぶされていないか、ユーザーに伝わるか、途中で失敗したときに不整合な状態が残らないか（再実行で揃うか） |
| セキュリティ | 権限の確認がサーバー側（DB）で強制されているか、入力・URL 由来の値をそのまま信用・表示していないか、秘密情報 |
| 並行・非同期 | コルーチンのキャンセル、二重送信・連打、読み込み中の再読み込み、古い結果での上書き |
| テスト | 追加・変更したロジック（domain・data の変換・ViewModel・DB のアクセス制御）にテストがあるか、テストが本当に失敗を検出できる書き方か |
| 設計 | 責務の置き場所（層）、既存の共通部品・関数の再利用、重複したロジック、不要な複雑さ |
| 可読性 | 名前と中身が一致しているか、周りのコードと書き方がそろっているか、理由の要るコードにコメントがあるか |
| 性能 | N+1、件数に比例して増えるリクエスト、不要な再描画・再読み込み |
| ドキュメント | 新しく決めた規約・ハマりどころが領域別ファイルに追記されているか、PR 本文・チェックリストが実際の変更と合っているか |

### 本アプリ固有の観点

`.github/skills/code-review/SKILL.md` の「重点的に確認すべき事項」のうち、差分に該当するものをすべて確認する。
「指摘しない事項」に該当するものは**指摘しない**（気付いても書かない）。

### 指摘にする前に確かめる

- 実際のコード（呼び出し元・呼び出し先・テスト・マイグレーション）を読んで、問題が本当に起きることを確かめる。
  **「どんな入力・状態で、何が起きるか」を具体的に書けないものは指摘にしない**（意図が分からないだけなら `[質問]` にする）。
- 既存のスレッド（解決済みを含む）で同じ指摘・同じ議論がされていれば、重ねて指摘しない。
- CI（`gh pr checks`）が失敗していれば、その原因を `[必須]` の指摘または概要コメントに書く。CI が見ている lint・テストの結果を
  レビューでなぞらない。

## 3. 指摘を書く

### 種別

| ラベル | 意味 | マージ前の対応 |
|---|---|---|
| 🔴 `[必須]` | バグ・セキュリティ・データの不整合・規約違反（根拠ファイルがあるもの） | 必要 |
| 🟡 `[推奨]` | テスト不足・保守性・分かりにくさなど、直したほうがよいもの | 任意（採用しない場合は理由を返信） |
| ❓ `[質問]` | 意図・前提の確認 | 返信が必要 |
| ⚪ `[軽微]` | 好みの範囲・細かな表記 | 任意 |

指摘には連番の ID（`R<回数>-<2桁の連番>`。例: 初回の3件目は `R1-03`）を付け、概要コメントの表とスレッドを対応させる。

### 行コメント（1指摘＝1スレッド）

指摘はその原因となる行（範囲なら `start_line`〜`line`）に付ける。差分の外の行（変更していない行）を指す必要がある場合も
そのまま書いてよい（投稿スクリプトが概要コメントの「差分外の指摘」に移す）。

````markdown
🔴 **[必須] R1-02: 更新が RLS で拒否されても成功として扱われる**

`update` に `select()` を付けていないため、他人の行を更新しようとして RLS で0行になってもエラーにならず、画面には「保存しました」と表示される。

- **観点**: RLS で0行になる変更（本アプリ固有）
- **根拠**: `.github/instructions/data.instructions.md`「DB アクセス（PostgREST）の実装パターン」
- **提案**: `select()` を付けて更新後の行を受け取り、0行なら `GenericDataFailureException` にする。

```suggestion
（そのまま置き換えられる修正案がある場合だけ書く）
```
````

- `suggestion` ブロックは、コメントを付けた行（範囲）をそのまま置き換えられる場合だけ使う（PR 上でそのまま適用できる）。
- 1つのコメントに複数の指摘を混ぜない（スレッドごとに対応・Resolve できるようにする）。
- 「根拠」は、本アプリ固有の観点なら根拠ファイルと節名を書く。標準的な観点で根拠ファイルが無ければ省いてよい。

### 概要コメント

````markdown
<!-- pr-review: round=1 head=<headRefOid> -->
## 🤖 Claude Code レビュー（1回目）

- 対象コミット: <headRefOid の先頭7文字>
- 結果: 🔴 必須 1 / 🟡 推奨 2 / ❓ 質問 1 / ⚪ 軽微 0

| ID | 種別 | 場所 | 指摘 |
|---|---|---|---|
| R1-01 | 🔴 必須 | `data/.../FooRepository.kt:42` | 更新が RLS で拒否されても成功として扱われる |

### 確認した観点

- 標準: 正しさ / エラー処理 / セキュリティ / 並行・非同期 / テスト / 設計 / 可読性 / 性能 / ドキュメント
- 本アプリ固有: （差分に該当して確認した項目を `.github/skills/code-review/SKILL.md` の観点名で列挙）

### 確認していないこと

- （例: 実ブラウザでの画面の確認、ローカルでの `./supabase/tests/run.sh` の実行。CI の結果は PR のチェックを参照）

### 対応のお願い

各スレッドに返信してから Resolve してください。採用した場合は修正コミット（SHA）と内容を、採用しない場合は理由
（方針で決まっている事項は根拠ファイルの該当箇所）を書いてください。`[必須]` がすべて対応済みになるまで Ready for review にしないでください。
````

指摘が0件なら、表の代わりに「指摘はありません」と書き、確認した観点・確認していないことは同じように残す。

## 4. 投稿する

1. セルフレビューのモードでは投稿せず、指摘の一覧を呼び出し元に返して終える。
2. 投稿内容を JSON にまとめる。形式はスクリプト冒頭の docstring を参照。`commit_id` には控えておいた `headRefOid` を入れる。
   ファイルには書かず、引数 `-` とヒアドキュメント（終端を引用符で囲み、本文の `$` や `` ` `` が展開されないようにする）で標準入力から渡す。
3. `--dry-run` で、行コメントにできる件数と差分外に移る指摘を確かめてから、同じ JSON で投稿する。

   ```sh
   python3 -I .claude/skills/pr-review/scripts/post_review.py --dry-run - <<'REVIEW_JSON'
   {"pr": <N>, "commit_id": "<headRefOid>", "body": "...", "comments": [...]}
   REVIEW_JSON
   python3 -I .claude/skills/pr-review/scripts/post_review.py - <<'REVIEW_JSON'
   （dry-run と同じ JSON）
   REVIEW_JSON
   ```

   - レビュー中に push されていた場合、スクリプトは投稿せずに終了する。新しいコミットの差分を確認し直してから投稿する。
   - レビューは常に `COMMENT` で投稿する（gh の認証ユーザーが PR 作成者と同じ場合、`REQUEST_CHANGES` / `APPROVE` は付けられない）。
     マージ可否の判断は概要コメントの結果（🔴 の有無）で示す。
4. 投稿したレビューの URL と指摘の一覧を呼び出し元に返す（「実行のされ方」の返す内容）。

## 5. 再レビュー（2回目以降）

1. 前回までの概要コメント（`<!-- pr-review: round=<n> head=<sha> -->`）から回数と前回の対象コミットを取り出す。
2. このスキルが付けた指摘（本文に `R<n>-<nn>` を含むスレッド）を、未解決・解決済みを問わず確認し、次のどれかにする。

   | 状態 | 判断の基準 | スレッドでの対応 |
   |---|---|---|
   | ✅ 対応済み | 返信の修正コミットで問題が解消している（コードを読んで確かめる） | 「✅ <SHA 先頭7文字> で修正を確認しました」と返信して Resolve |
   | 🤝 採用しない（合意） | 返信の理由が妥当（方針・根拠ファイルに沿う、指摘の前提が誤り等） | 「🤝 理由を確認しました。このままで問題ありません」と返信して Resolve |
   | ⏳ 未対応 | 返信が無い／修正が不十分／理由に同意できない | 何が足りないかを返信し、Resolve しない（作成者が Resolve 済みなら、未解決に戻さず返信だけする） |

   返信・Resolve は `scripts/threads.py` で行う（トップレベルの PR コメントで返信しない）。

   ```sh
   # スレッドへ返信（本文に ' を含む場合は '\'' で書く）
   python3 -I .claude/skills/pr-review/scripts/threads.py reply <thread id> '<返信本文>'
   # スレッドを Resolve
   python3 -I .claude/skills/pr-review/scripts/threads.py resolve <thread id>
   ```
3. 前回の対象コミットからの変更を、2.〜3. と同じ手順でレビューする。修正のために入った変更が新しい問題を起こしていないかを重点的に見る。
   - 前回の対象コミットからのこの PR 自身の変更は、PR のコミットだけを辿って求める（`git log --no-merges <前回の sha>..<headRefOid>` の
     各コミットの差分）。`git diff <前回の sha>..<headRefOid>` は、間に main をマージしている（アプリの「ベースブランチと同期」を含む）と
     main 側で入った他の PR の変更まで含むため、そのまま使わない。
   - 指摘は、今の PR の差分（`gh pr diff`）に含まれる行だけに付ける。force push で前回の sha が無い場合は PR 全体をレビューする。
4. 概要コメントを `round=<n+1>` で投稿する。表の前に、前回までの指摘の状態の表を付ける。

   ```markdown
   ### 前回までの指摘

   | ID | 種別 | 状態 |
   |---|---|---|
   | R1-01 | 🔴 必須 | ✅ 対応済み（abc1234） |
   | R1-02 | 🟡 推奨 | 🤝 採用しない（合意） |
   | R1-03 | ❓ 質問 | ⏳ 未対応 |
   ```

## このスキルを更新するとき

- 本アプリ固有の観点（指摘しない事項・重点的に確認すべき事項）を増やすときは、このファイルではなく
  `.github/skills/code-review/SKILL.md` に根拠ファイルとあわせて追加する（`copilot-construction.md`「6. このドキュメントの更新方針」）。
- このファイルには、レビューの進め方・指摘の書き方・PR への記録の仕方だけを書く。
- サブエージェントは呼び出し元の会話を見られないため、手順に必要なコマンド・前提はこのファイルの中で完結させる
  （「さっきの」「会話で決めた」等、呼び出し元の文脈に頼る書き方をしない）。使うコマンドを増やしたら、frontmatter の
  `allowed-tools` にも追加する。
